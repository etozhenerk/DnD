# Постоянная CPU-модель для разработки

Бюджетная ВМ `dnd-llm-qwen35-dev` (`fhmbp5ngff75mbh24j8s`) в каталоге `b1g8siv8ve2si1qp04nm` работает постоянно: `standard-v4a`, 8 vCPU, 16 ГБ RAM, Ubuntu 24.04, сетевой SSD 40 ГБ. Статический публичный IP — `89.169.139.143`. На ней запускается [Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B) в [GGUF Q4_K_M](https://huggingface.co/unsloth/Qwen3.5-9B-GGUF/tree/main) через CPU-контейнер `llama.cpp`. Веса (около 5,68 ГБ) загружаются **только на диск ВМ**. После первого скачивания модель открывается напрямую с диска без запроса к Hugging Face при каждом запуске. Контекст сервера — 16 384 токена, разделённых между двумя параллельными слотами, то есть до 8192 токенов на запрос. Это режим для разработки и проверки сценарных переходов, не замена 27B для финальной оценки качества.

Публичный пробный чат: [http://89.169.139.143:8080/](http://89.169.139.143:8080/). Это копия интерфейса GPU-пилота: режимы, потоковая выдача, Markdown, мобильная верстка. Только подпись модели изменена на Qwen3.5-9B. API `llama.cpp` слушает `127.0.0.1:8000` на самой ВМ. Речь и данные кампании не подключены.

## Развёртывание

Скрипты установки и HTML упаковываются в `user-data` через `make-boothook.py`. В `user-data` **нет весов модели**. После добавления метаданных ВМ перезапускается; cloud-init копирует файлы в `/opt/dnd-llm`, ставит Docker, скачивает образ и затем веса напрямую с Hugging Face. Сервисы `dnd-qwen35` и `dnd-trial-ui` автоматически запускаются после перезагрузки.

```bash
python3 infra/llm-cpu/make-boothook.py /tmp/dnd-llm-cpu-boothook.sh
yc compute instance add-metadata dnd-llm-qwen35-dev \
  --folder-id b1g8siv8ve2si1qp04nm \
  --metadata-from-file user-data=/tmp/dnd-llm-cpu-boothook.sh
yc compute instance restart dnd-llm-qwen35-dev \
  --folder-id b1g8siv8ve2si1qp04nm
yc compute instance get-serial-port-output dnd-llm-qwen35-dev \
  --folder-id b1g8siv8ve2si1qp04nm --port 1 | rg DND_CPU
```

На ВМ лог установки находится в `/var/log/dnd-llm-cpu-bootstrap.log`; логи модели — `journalctl -u dnd-qwen35`. Состояние API: `curl http://127.0.0.1:8000/health`. Публичный интерфейс показывает готовность на `/health` своего порта `8080`.

## Стоимость и ограничения

По [тарифам Compute Cloud](https://yandex.cloud/ru/docs/compute/pricing) текущие 8 vCPU и 16 ГБ RAM обходятся ориентировочно в **11 916 ₽/30 дней** с SSD 40 ГБ и активным публичным IP, без трафика и прочих сервисов. Это примерно на **3629 ₽/30 дней** больше прежней конфигурации 4 vCPU. Остановленная A100 отдельно сохраняет платный SSD 150 ГБ и зарезервированный IP (примерно 2584 ₽/30 дней). При двух коротких одновременных запросах 4 vCPU завершали оба за 7,1–7,3 с, а 8 vCPU — за 4,3 с. Два разных игровых запроса на 8 vCPU начали отдавать текст через 5,2–5,6 с и завершились за 19,8–21,9 с. В отдельной проверке два полностью одинаковых длинных запроса были обработаны последовательно; два разных игровых запроса шли параллельно. Холодная загрузка 5,7 ГБ GGUF с диска этой ВМ занимает несколько минут; она не отражает скорость уже прогретого ответа.

При создании ВМ диск 80 ГБ не прошёл квоту SSD каталога, поэтому использован 40 ГБ. Это достаточный стартовый объём для одной Q4-модели и контейнера; свободное место следует проверять после установки. Для долгого сценария 8192 токена на запрос потребуют резюме истории и выборки релевантного лора на будущем бэкенде. Начиная с третьего одновременного запроса CPU-модель ставит запросы в очередь.
