# Этап 5. Авторизация и владение персонажами

Статус: согласован; после конструктора персонажей.

Короткое название: Вход для друзей.

Краткое описание: Добавляем Яндекс ID, список «Мои» и редактирование своих персонажей.

Родительский документ: [Продуктовый roadmap](../product-roadmap.md).

## Цель

Добавить персональный вход через Яндекс ID, привязку новых персонажей к создателю и право редактировать свои готовые карточки.

Сейчас конструктор работает без пользовательской авторизации. Общий пароль редактора не вводится: каждый анонимный черновик защищён своим токеном. Пользовательские аккаунты и «Мои» подключаются на этом этапе.

## Результат для пользователя

- Разрешённый участник входит через Яндекс ID и выходит из сервиса.
- В конструкторе доступны общий список «Все» и личный список «Мои».
- Новый персонаж после входа связывается с его создателем.
- Участник продолжает свой черновик и может редактировать свою завершённую карточку.
- Сервер проверяет права на каждую операцию; скрытой кнопки во фронтенде недостаточно.

Игровые комнаты, сбор партии и роли мастера конкретной игры относятся к этапу 7.

## Согласованные границы

- Для входа используется Яндекс ID; самостоятельная регистрация и интерфейс приглашений не добавляются.
- Доступ получают заранее разрешённые друзья; список доступа управляется через бэкенд.
- Пользовательская авторизация и редактирование готовых карточек появляются вместе, после первой версии конструктора.
- Поле `creator_user_id` уже предусмотрено в схеме и может быть `NULL`.
- Карточки, созданные анонимно, сохраняются без автоматического назначения создателя.
- Вкладка «Мои» не имитируется метками одного браузера до входа.
- История ревизий не является обязательным условием редактирования в первой версии.
- Добавление персонажа в каноническую книгу — отдельное решение.

## Серверная часть

- Добавить интеграцию Яндекс ID и собственные отзываемые сессии приложения.
- Дополнить предусмотренную модель пользователей данными входа и списком разрешённых аккаунтов.
- Связывать новые черновики и персонажей с текущим пользователем на сервере.
- Реализовать выборку «Мои» по `creator_user_id`, сохранив общий список готовых карточек.
- Добавить операции редактирования готовой карточки с проверкой создателя и баланса.
- Согласовать правила административного доступа и возможной привязки анонимных карточек до реализации этих операций.
- Обновить YAML-контракт, серверные проверки и CORS/cookie-настройки для выбранных адресов фронтенда и API.

Существующая схема описана в [архитектуре БД](../architecture/character-database.md). Серверная авторизация не заменяется CORS или клиентским спойлер-барьером.

## Последовательность реализации

1. Уточнить границу закрытого контента, административные права и работу с анонимными карточками.
2. Зарегистрировать интеграцию Яндекс ID и зафиксировать HTTP-контракт входа и сессии.
3. Добавить необходимые миграции, серверную сессию и проверки доступа к объектам.
4. Связать новые персонажи с создателем и реализовать список «Мои».
5. Реализовать серверное редактирование своих готовых карточек без обязательной истории версий.
6. Добавить вход, выход, профиль, «Мои» и доступные действия в конструкторе.
7. Проверить права прямыми API-запросами и пройти пользовательский сценарий в браузере.

## Критерии завершения

- Разрешённый участник может войти и выйти; истёкшая или отозванная сессия не даёт доступа.
- Создатель нового персонажа определяется сервером, а не переданным клиентом ID.
- «Мои» содержит только карточки текущего пользователя; общий список работает согласно согласованной видимости.
- Чужую карточку нельзя изменить прямым запросом к API.
- Редактирование сохраняет действующий баланс характеристик и навыков.
- Анонимные карточки и их стабильные ID не теряются при внедрении авторизации.
- OAuth-токены не передаются во фронтенд и не попадают в логи.
- Контракт, серверные проверки и браузерная приёмка обновлены.

## Открытые решения перед реализацией

- Какие страницы и чтение данных останутся доступными до входа.
- Как разрешённый участник подтверждает право на ранее созданную анонимную карточку, если такая привязка понадобится.
- Какие операции разрешены администратору и как фиксируется их выполнение.
- Срок жизни сессии и политика конкурентного редактирования.
- Единый HTTPS origin или работа с разными адресами и соответствующие cookie/CORS-настройки.

Это будущий этап. Его техническая детализация не блокирует текущую реализацию конструктора без авторизации.
