# Бэкенд

Go API конструктора новых персонажей «Хроник Восьми Земель». Контракт находится в [`shared/api/openapi.yaml`](../shared/api/openapi.yaml). Он не меняет шесть готовых героев в `content/` и не добавляет карточки в общую книгу.

Обязательные соглашения для нового кода: [CODE_STYLE.md](CODE_STYLE.md). Они определяют границы пакетов, обработку ошибок и context, работу с PostgreSQL, HTTP-контракт и приёмку изменений.

CI проверяет форматирование новых Go-файлов через `scripts/check_code_style.py`; существующие пути из `code-style-baseline.json` исключены из этой проверки. Сборки и тесты в текущей рабочей сессии выполняются в CI. `go test -race ./...` включает HTTP/SQL-тесты на отдельной PostgreSQL 17: каждый тест получает собственную временную схему. Ответы options/validate/read дополнительно сверяются с OpenAPI. Production-БД эти тесты не используют; [PostgreSQL service container](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers) работает только внутри job.

## Локальная проверка и запуск

```bash
go test ./...
go vet ./...
DATABASE_URL='postgres://...' CORS_ALLOWED_ORIGINS='https://example.org' go run ./cmd/api
```

`go` запускается из `backend/`. Сервер слушает `PORT` (по умолчанию `8080`) и читает канонические `../content/character-creation.json`, `../content/races.json` , `../content/character-abilities.json` и `../content/rules.json`. Контейнер включает эти четыре файла и задаёт `CONTENT_DIR`. Для локального запуска используйте `DATABASE_URL`. В облаке используются отдельные `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_NAME`, `DB_PASSWORD`, `DB_SSL_ROOT_CERT`; пароль приходит из Lockbox, TLS проверяет сертификат и имя хоста (`verify-full`). База доступна только из облачной сети. Пул каждого экземпляра API ограничен двумя соединениями.

`CORS_ALLOWED_ORIGINS` — список полных origin через запятую: схема, домен и при необходимости порт, без пути и завершающего `/`. Укажите действительный адрес фронтенда при развёртывании. `*` не поддерживается. Разрешены `GET`, `POST`, `PATCH`, предварительный `OPTIONS`, заголовки `Authorization` и `Content-Type`. Авторизации пользователя пока нет. Все операции `/drafts` возвращают `403 drafts_require_authentication`, даже со старым Bearer-токеном: такой токен не является личностью пользователя.

## Состояние API

- `GET /creator/options` возвращает `rulesetId: character-creation-v3`, 12 классов, семь рас и `abilityRules`: бесплатную базовую атаку, семь профилей навыков, отдельный бюджет 6 и пределы. Характеристики и HP/AC остаются из [`content/character-creation.json`](../content/character-creation.json), навыки — из [`content/character-abilities.json`](../content/character-abilities.json).
- V3 добавляет неснижаемую основу каждого класса стоимостью 10 и 4 очка усиления. API возвращает описания, стиль и слабые стороны класса; сервер проверяет основу по classId. Прежние v1/v2 сохраняют свободное распределение, а готовые персонажи читаются из собственного снимка.
- Готовые персонажи доступны через `GET /characters` и `GET /characters/{id}`. `POST /characters` принимает целую анкету v3 без серверного черновика: проверяет баланс и атомарно сохраняет героя, навыки и предметы с `creator_user_id = NULL`. Редактирование готовой карточки не открыто.
- Создание, чтение, PATCH, validate, complete, advice и assets для черновиков закрыты общим HTTP-ограничением до авторизации и проверки владельца. При отказе API не читает и не меняет БД. Таблица и ранее созданные тестовые анкеты сохранены; старый токен не открывает к ним доступ. У frontend-формы нет серверного ID или токена черновика.
- Внутренняя механика сохранения разделов, валидации и атомарного завершения остаётся подготовкой будущих авторизованных черновиков. Её HTTP/SQL-тесты используют отдельный внутренний handler только в тестах и временную PostgreSQL CI. Отдельные тесты production-handler проверяют отказ для каждого действия с токеном и без него. Механика v2/v3 вычисляет HP/AC и расход очков навыков; v1 сохраняет прежние правила описательных навыков.
- В `abilities` v2/v3 игрок задаёт `basicAction`, до трёх `items` с `profileId`/`modifierStat` и до трёх `narrativeItems`. Неизвестные поля и неверные типы дают 400 при PATCH; неполный раздел можно сохранить. При validate/complete сервер проверяет бюджет, уникальность ID и профилей, характеристики и лимиты, затем вычисляет кубики, заряды, бонус атаки и `effectText`. Клиентские `effects`, `uses`, `points`, `trigger` и `effectText` не принимаются.
- Готовая карточка хранит базовую атаку, активные навыки и повествовательные особенности в упорядоченном `abilities`. Формальные эффекты имеют `automationMode: automatic` и снимок механики с `profileId` и версией в JSONB; чтение восстанавливает эти данные без пересчёта. Это описание для будущего игрового runtime, его запуск здесь не реализован. Повествовательные особенности, старые навыки v1 и предметы остаются ручными описаниями.
- AI Studio и хранилище портретов/иконок ещё не подключены. Их внутренние обработчики остаются заглушками; внешний отказ до авторизации — `drafts_require_authentication`.

## Сохранение и кэш публичного чтения

`POST /characters` требует `requestId` (UUID будущей карточки), текущий `rulesetId` и все шесть разделов `formData`. Нормализованная анкета получает SHA-256 в `creation_request_hash`; UUID и сравнение хэша обеспечивают повтор через любой экземпляр API. Первый запрос возвращает 201, неизменённый повтор — 200 с тем же временем создания, другая анкета с занятым ID — 409. UUID не предоставляет право редактирования или владения. Текущий маршрут не принимает создателя, HP/AC, формальные эффекты, портреты и числовые эффекты предметов. Проверка правил выполняется перед записью; ошибки 422 содержат пути полей. Лимит JSON — 256 КиБ.

Успешное создание и повторное подтверждение через `POST /characters` сбрасывают кэш текущего процесса. Для первого списка после сохранения клиент запрашивает `fresh=true`: чтение обходит кэш любого экземпляра и показывает актуальную БД (`read_cache=bypass`). Обычные чтения продолжают использовать короткий кэш.

`internal/httpapi` объединяет одновременные одинаковые чтения и хранит успешные JSON-ответы в памяти одного экземпляра API: каталог — 5 минут, список — 15 секунд, карточка — 1 минуту. Лимит — 128 записей по 256 КиБ (до 32 МиБ тел ответов). Redis и дополнительные облачные ресурсы не нужны.

Ключ учитывает путь и параметры запроса; ошибки, черновики, запросы с Authorization/Cookie и ответы с приватными заголовками не сохраняются. CORS и ограничение доступа выполняются перед кэшем при каждом запросе. Успешное внутреннее завершение персонажа очищает кэш и препятствует сохранению устаревшего ответа из параллельного чтения. Внешний доступ к черновикам остаётся закрытым.

`Server-Timing` показывает время приложения (`app`) и `read_cache` (`hit`/`miss`); CORS разрешает чтение этого заголовка. HTTP-ответы имеют `Cache-Control: no-store`: браузерный кэш запросов контролирует TanStack Query. Диагностика приложения не включает сеть, API Gateway и запуск контейнера после простоя; после перезапуска кэш пустой. Проверки TTL, параллельности, отмены, границ, сброса и CORS входят в Go CI.

## PostgreSQL

Миграция [`000001_character_creator.up.sql`](migrations/000001_character_creator.up.sql) применена 29 сентября 2026 года к базе `dnd` кластера `dnd-characters-pg` через Yandex WebSQL. Она создаёт `schema_migrations`, `users`, `character_drafts`, `characters`, `character_abilities`, `character_items` и `character_assets`. Повторно запускать файл в этой базе нельзя. Схема и сетевые параметры описаны в [`docs/architecture/character-database.md`](../docs/architecture/character-database.md) и [`docs/architecture/yandex-postgres.md`](../docs/architecture/yandex-postgres.md).

Миграция [`000002_api_permissions.up.sql`](migrations/000002_api_permissions.up.sql) применена 30 сентября 2026 года: пользователь `dnd_api` получает права на черновики и чтение/создание готовых персонажей. Он не управляет схемой, пользователями и миграциями.

Миграция [`000003_character_creation_request.up.sql`](migrations/000003_character_creation_request.up.sql) применена 1 октября 2026 года через WebSQL: добавляет необязательный хэш анкеты и ограничение длины 32 байта. Прежние записи сохраняют NULL; их UUID не принимается как повтор нового сохранения. Версия, тип колонки, CHECK и INSERT-права приложения проверены; новых IAM/SQL-прав не выдавалось.

## Контейнер и деплой

Образ собирается из корня репозитория:

```bash
docker build -f backend/Dockerfile -t dnd-api .
```

Workflow [deploy-yandex-backend.yml](../.github/workflows/deploy-yandex-backend.yml) проверяет Go, собирает образ и публикует API из `main`. Секретов GitHub и постоянных ключей CI нет: используется OIDC. Параметры облака, HTTPS адрес и порядок проверки описаны в [yandex-backend.md](../docs/architecture/yandex-backend.md).
