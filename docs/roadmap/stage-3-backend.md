# Этап 3. Облачная инфраструктура и Go API

Статус: завершён — облачная основа запущена.

Дата актуализации: 30 сентября 2026 года.

Короткое название: Сервисы в облаке.

Краткое описание: Фронтенд, Go API, PostgreSQL и автодеплой уже работают в Yandex Cloud.

Родительский документ: [Продуктовый roadmap](../product-roadmap.md).

## Цель

Подготовить облачную основу для конструктора персонажей: независимые фронтенд и Go-сервис, PostgreSQL, HTTP-контракт и воспроизводимый деплой из `main`.

Первоначальный план полного переноса всех JSON в БД уточнён: сначала создаём новых персонажей через API. Существующий канон и книга героев остаются без изменений до отдельного этапа миграции.

## Выполнено

- Репозиторий разделён на `frontend/`, `backend/`, `shared/`, `content/`, `docs/`, `infra/` и `skills/`.
- React, TypeScript, npm-конфигурация и визуальные ассеты находятся во `frontend/`; Go modules — в `backend/`. В корне нет `package.json` или `go.mod`.
- Общий HTTP-контракт зафиксирован в YAML OpenAPI в `shared/api/openapi.yaml`.
- Фронтенд развёрнут в Yandex Object Storage; публикация из `main` настроена через GitHub Actions. GitHub Pages также продолжает обновляться.
- Go API развёрнут в приватном Serverless Container за HTTPS API Gateway. Отдельная виртуальная машина для API не создавалась.
- Созданы Container Registry, Lockbox и Managed PostgreSQL; SQL-схема конструктора применена к облачной БД.
- Настроены сервисные аккаунты, доступ CI через OIDC, приватное подключение API к PostgreSQL и CORS для фронтенда.
- API поддерживает черновики, проверку и завершение персонажа, чтение списка и отдельной карточки.
- Сервер рассчитывает HP/AC и проверяет распределение характеристик и навыков по утверждённым правилам.
- В CI работают Go-проверки, интеграционные тесты с PostgreSQL и проверка HTTP-ответов по OpenAPI. Деплой API проверяет живые ручки после публикации.

Фактическая конфигурация и порядок деплоя описаны в [архитектуре API](../architecture/yandex-backend.md), [настройке PostgreSQL](../architecture/yandex-postgres.md) и [схеме конструктора](../architecture/character-database.md).

## Текущая архитектура

- Браузер загружает статический React-фронтенд из Object Storage либо GitHub Pages.
- Конструктор будет обращаться к HTTPS API Gateway; шлюз вызывает Go-контейнер.
- Go-сервис сохраняет новые карточки в PostgreSQL через приватную облачную сеть.
- Пароль подключения передаётся контейнеру из Lockbox.
- Каждый анонимный черновик защищён собственным случайным токеном; пользовательская авторизация пока отсутствует.
- Фронтенд и API имеют разные origin, поэтому сервер обрабатывает CORS и preflight.

Все приложения ещё не переключены на API: существующая карта, книга и кампании продолжают читать канонические JSON. Это сохраняет их работу во время разработки конструктора.

## Источники данных

- `content/**/*.json` — действующий канон мира, кампаний, существующих героев и утверждённых правил.
- PostgreSQL — сохранённые черновики и новые персонажи конструктора.
- `frontend/assets/concepts/` — утверждённые визуальные материалы и manifest.
- `shared/api/openapi.yaml` — общий транспортный контракт; TypeScript не выносится из `frontend/`.

Существующие герои не импортированы в БД и не пересчитываются по правилам конструктора. Завершение нового персонажа не добавляет его в каноническую книгу.

## Отложенные задачи

### Перенос существующего канона в PostgreSQL

Выполняется отдельным согласованным шагом после текущей работы над конструктором:

- определить, какие сущности мира действительно должны обслуживаться API;
- спроектировать таблицы и публичные DTO без потери данных и секретов мастера;
- импортировать данные транзакционно с сохранением стабильных `id`;
- сравнить исходные JSON и ответы API;
- подключить затронутые страницы к серверу и проверить их поведение;
- обновить источники истины только после успешного переключения.

До этого `content/` остаётся рабочим каноном, а не историческим снимком.

### Доставка фронтенда и медиа

Фронтенд сейчас раздаётся напрямую из Object Storage. Единый HTTPS origin и собственный домен ещё не настроены. Раздача тяжёлых медиа через API Gateway требует отдельного решения; текущие ассеты не переносятся в шлюз автоматически.

Отключение GitHub Pages, выделение хранилища медиа и перенос существующих страниц на API не считаются выполненными задачами.

## Критерии готовности облачной основы

- Разделены фронтенд, Go-сервис и общий YAML-контракт.
- Фронтенд и API публикуются из `main`.
- API доступен по HTTPS и работает с облачной PostgreSQL.
- Секреты не хранятся в репозитории и браузере.
- Создание, валидация, завершение и чтение персонажей реализованы на сервере.
- CI проверяет бэкенд и контракт; существующие frontend-проверки сохранены.
