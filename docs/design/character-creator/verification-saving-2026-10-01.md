# Проверка сохранения персонажа — 1 октября 2026

## Область

Первый следующий этап после опубликованного UI: целая готовая анкета → серверная проверка → PostgreSQL → карточка и список. Портреты/иконки, советник, вход и редактирование сюда не входят. Канонические герои и правила не менялись.

## Реализация

- YAML описывает `POST /characters`: v3, полная анкета, UUID попытки, 201/200/409/422 и лимит JSON 256 КиБ. Создатель не принимается от клиента; до авторизации он NULL.
- HTTP, сценарий, утверждённая предметная валидация и SQL разделены. Неизвестные поля, лишний JSON и запрещённые null отклоняются. HP/AC и механика навыков рассчитываются сервером.
- Один UUID и SHA-256 нормализованной анкеты защищают неизменённый повтор, включая два запроса через разные экземпляры. Персонаж и дочерние строки записываются одной транзакцией. Другая анкета с тем же UUID получает 409.
- Frontend использует mutation без автоматического повтора, блокирует повторное нажатие и текущую форму при отправке. Ошибки 422 показывают ссылки на нужный этап; при сбое анкета остаётся в памяти. Успех заполняет кэш карточки, обновляет список чтением `fresh=true` и открывает героя. Уход со страницы во время запроса не вызывает позднего принудительного перехода.
- Локальные изображения не отправляются. При их наличии нужен явный выбор «Сохранить без изображений»; иначе игрок остаётся в форме.

## БД

`000003_character_creation_request` применена через WebSQL к существующей БД `dnd` от имени `dnd_owner`. В живой БД проверены версия миграции, колонка bytea, CHECK на NULL/32 байта и унаследованные INSERT-права `dnd_api`. Старые записи не изменены. Новые IAM-права, машины и платные ресурсы не добавлены. ## Проверки

- `git diff --check` и форматирование новых Go-файлов. Локальные сборки, typecheck и тесты не запускались по решению автора.
- Для CI добавлены HTTP/SQL-проверки полного цикла и повторного запроса, конкурентной отправки, конфликта, отката при сбое дочерней записи, отмены, невалидного бюджета, закрытых черновиков и свежего чтения между экземплярами. Фактические запрос/ответы сверяются с YAML.
- Frontend-regression проверяет сохранение UUID при повторе, новый UUID при изменении формы, отсутствие вычисляемых полей в отправке и отображение путей серверной ошибки.
