# Портреты и иконки конструктора

## Передача и хранение

`POST /characters` сохраняет готовую анкету. Для героя без изображений остаётся JSON;
с изображениями используется `multipart/form-data`: поле `character` с JSON,
необязательный `portrait`, до трёх полей `icon:<abilityId>`. Base64 не применяется.

Конструктор принимает PNG/JPEG/WebP до 10 МиБ и позволяет сравнивать восемь портретов.
В облако отправляется выбранный портрет. Браузер сохраняет пропорции, не кадрирует,
перекодирует PNG/WebP в PNG с прозрачностью, JPEG в JPEG и удаляет исходные метаданные.
Размеры отправки: портрет до 1600 px по длинной стороне и 1 МиБ;
иконка до 512 px и 128 КиБ. При необходимости уменьшается разрешение.
JSON до 256 КиБ; всё multipart-тело до 2 МиБ, включая служебные поля.
Это оставляет запас относительно [лимита API Gateway 2,5 МБ](https://yandex.cloud/en/docs/api-gateway/concepts/limits).

Сервер проверяет фактический формат, размеры, декодируемость, наличие активного навыка,
количество и дубли частей. Только PNG/JPEG; SVG и произвольные ссылки не принимаются.
HP/AC и эффекты по-прежнему вычисляются по правилам v3.

Изображения неизменяемы: UUID и ключ объекта зависят от персонажа, назначения,
ID навыка и SHA-256 файла. `If-None-Match: *` исключает перезапись, повтор сверяет содержимое.
Ссылки на медиа входят в отпечаток анкеты: другая картинка при том же requestId даёт 409.
Фронтенд создаёт новую попытку после смены выбранного портрета или иконки.

## База и чтение

Миграция `000004_character_media` делает FK портрета отложенным до конца транзакции.
Миграция `000005_media_permissions` даёт `dnd_api` SELECT/INSERT на существующую
`character_assets`. UPDATE/DELETE не нужны. Runtime не мигрирует схему.

Одна SQL-транзакция создаёт персонажа, проверенные метаданные файлов, навыки с иконками
и предметы. Ошибка приводит к rollback всех строк. creator_user_id остаётся NULL.

`GET /characters` и `GET /characters/{id}` возвращают `portraitUrl`; навыки —
`iconAssetId` и `iconUrl`. URL вида `/assets/<uuid>` разрешается относительно API.
`GET /assets/{assetId}` читает только verified-файл, который связан с портретом
или навыком своего сохранённого персонажа. Отсутствующий или непривязанный файл — 404.
Ответ содержит проверенные бинарные байты, MIME, nosniff, SHA-256 ETag,
`Cache-Control: public, max-age=31536000, immutable`; условный запрос возвращает 304.
Без портрета применяется утверждённая заглушка.

## Стоимость и ограничения

По [правилам тарификации Object Storage](https://yandex.cloud/ru/docs/storage/pricing)
первый 1 ГиБ STANDARD и первые 10 000 операций записи / 100 000 чтения в месяц
не тарифицируются. Квоты общие с прочим использованием сервиса.
В опубликованном расчёте ставка хранения — 2,376 ₽/ГиБ/месяц с НДС;
оценка полного бакета — около 2,4 ₽/месяц до бесплатной квоты.
Это оценка хранения; запросы API Gateway/контейнера и исходящий трафик считаются отдельно.
Сто героев с максимальным портретом и тремя иконками — до 138 МиБ.

Object Storage и PostgreSQL не имеют общей транзакции. Файлы загружаются перед SQL:
при сбое БД/отмене запроса или конфликте могут остаться непривязанные объекты.
Они не доступны через API. Повтор успешной попытки использует те же ключи.
Удалять такие файлы автоматически при ошибке нельзя: параллельная попытка могла их сохранить.
При обслуживании сверять ключи бакета с `SELECT object_key FROM character_assets`,
учитывать активные запросы и удалять только старые подтверждённые остатки.
Лимит 1 ГиБ ограничивает объём; при заполнении новые загрузки завершатся ошибкой.

Анонимное создание остаётся публичным. Авторизация и привязка к создателю — отдельный этап.
Редактирование изображений существующих героев в этой версии закрыто.
