# Правила нового Go-кода

Обязательные соглашения для нового и существенно изменяемого кода в `backend/`. Общие ограничения проекта находятся в [AGENTS.md](../AGENTS.md), HTTP-контракт — в [OpenAPI YAML](../shared/api/openapi.yaml).

Основа — [Google Go Style Guide](https://google.github.io/styleguide/go/guide): понятное поведение, простые конструкции и минимум ненужных зависимостей. Числовые ориентиры размера и структура нашего API ниже — решения проекта. Они не выдаются за требования языка Go.

Существующий сервис целиком не переписываем. Новую функцию не добавляем в большой файл только потому, что прежний код уже устроен так. Выделяем необходимую часть по ответственности, сохраняя действующее поведение.

## 1. Пакеты и зависимости

Пакет объединяет одну понятную ответственность. Не вводим универсальные `utils`, `common`, `helpers`, `types` и `interfaces`. Имена пакетов короткие, в нижнем регистре; имена типов не повторяют имя пакета. Основание — [рекомендации команды Go по именам пакетов](https://go.dev/blog/package-names).

Направления для нового кода:

| Место | Ответственность |
| --- | --- |
| `cmd/api` | Чтение конфигурации, создание зависимостей, запуск и остановка сервера |
| `internal/httpapi` | Маршруты, middleware, HTTP DTO, декодирование запросов и ответы |
| `internal/characterapp` | Сценарии конструктора: сохранить, проверить, завершить, запросить совет |
| `internal/creator` | Предметные типы, проверка анкеты и вычисление игровых характеристик |
| `internal/storage` | PostgreSQL, SQL, преобразование строк БД, транзакции |
| `internal/aistudio` | Клиент внешнего AI API, когда начнётся интеграция |
| `migrations` | Последовательные SQL-миграции |

Новые пакеты создаём только вместе с задачей, которой они нужны; пустые слои заранее не создаём. Уже существующие функции в `cmd/api`, `creator` и `storage` автоматически не переносим.

Границы:

- `cmd/api` связывает реализации. В нём не появляются новые обработчики, SQL и игровые формулы.
- HTTP-обработчик разбирает запрос, проверяет транспортные ограничения, вызывает сценарий и преобразует результат в HTTP. Он не проводит транзакцию и не считает баланс.
- Сценарий знает предметную модель и необходимые интерфейсы зависимостей. Он не зависит от `http.Request`, `http.ResponseWriter`, `pgx` и SDK облака.
- Чистые игровые правила не обращаются к сети и БД. Загрузка каталога и внешние вызовы не смешиваются с вычислением правил.
- Storage не импортирует HTTP или сценарии; работает с предметными значениями. Код сценария не импортирует конкретный storage: реализацию передаём при запуске.
- Модели HTTP и БД не экспортируем случайно в качестве публичного контракта. DTO и преобразования размещаем у соответствующей границы; отдельный тип нужен, когда формы или обязанности различаются.

Пример зависимостей: `httpapi → characterapp → creator`; `storage → creator`. Реализацию storage получает `characterapp` через небольшой интерфейс, который определяет сам потребитель.

## 2. Простая организация кода

- Перед новой зависимостью проверяем возможности языка, стандартной библиотеки и уже подключённых пакетов.
- Зависимости передаём явно через конструктор. Глобальные изменяемые сервисы, service locator и скрытая инициализация через `init()` запрещены.
- Интерфейс создаём у потребителя, когда есть реальная граница или необходимость подмены. Только нужные методы; конструктор реализации обычно возвращает конкретный тип. Не создаём интерфейс на каждый struct. Основание — [Google Go Style Decisions](https://google.github.io/styleguide/go/decisions#interfaces).
- Используем типизированные параметры. `map[string]any` и `json.RawMessage` допустимы на действительно динамической границе, но не заменяют типы известного сценария.
- Файл именуем по задаче: `drafts.go`, `validation.go`, `tokens.go`. Не складываем маршруты, SQL, токены и конфигурацию в один `main.go` или `service.go`.
- Цель функции — 20–50 строк. После 80 строк пересматриваем ответственность; цель написанного вручную файла — до 300 строк. Большой файл делим по смыслу, не создавая десятки бессодержательных обёрток. Крупные таблицы тестов и сгенерированные файлы оцениваем отдельно.
- Не уплотняем код в одну строку ради этих ориентиров. Именованные константы объясняют лимиты и единицы измерения.

## 3. Идиомы Go

- Форматирование — `gofmt`; не обсуждаем ручной вариант отступов и расположения скобок.
- Экспортируем только необходимый API. У экспортированных сущностей есть комментарий, объясняющий контракт; комментарии сложного кода объясняют причину решения.
- Пишем `characterID`, `HTTPClient`, `URL`, а не `characterId`, `HttpClient`, `Url`.
- Сначала обрабатываем ошибку или ранний выход, затем основной путь. Не прячем его во вложенные `else`.
- `error` — последний возвращаемый результат. Пустая строка или `-1` не заменяют ошибку. `bool` подходит, когда важно только наличие значения.
- Избегаем голых `return` в нетривиальной функции. Имена аргументов и результата помогают понять смысл, а не только сокращают код.
- Receiver имеет короткое стабильное имя. Мутабельные структуры и структуры с mutex передаём без копирования; не смешиваем случайно value и pointer receivers.

Эти соглашения адаптированы из [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments).

## 4. Ошибки и логи

- Проверяем все ошибки. Намеренное игнорирование требует понятной причины рядом с кодом; ошибки `Commit`, декодирования и записи данных не игнорируем.
- Добавляем безопасный контекст операции через `fmt.Errorf("load draft: %w", err)`. Для классификации используем `errors.Is` / `errors.As`, а не поиск подстроки в `err.Error()`. Основание — [официальное описание ошибок Go](https://go.dev/blog/go1.13-errors).
- Наличие объекта, невалидная анкета, запрет доступа и сбой зависимости — разные результаты. HTTP-коды и стабильные коды ошибок переводятся в транспортном слое по OpenAPI.
- Ошибку либо возвращаем выше, либо обрабатываем и логируем. Один сбой не логируем на каждом слое.
- Обычная ошибка пользователя или внешнего сервиса не вызывает `panic`. Завершение процесса допустимо при невозможности запуска и только в точке входа после освобождения ресурсов.
- Для нового журналирования используем стандартный `log/slog` со структурированными полями: операция, request ID, безопасный код ошибки, длительность. Основание — [документация `slog`](https://pkg.go.dev/log/slog).
- Не выводим токены, пароль, DSN, заголовок `Authorization`, полный ответ AI и содержимое анкеты. Сырая ошибка SDK или драйвера тоже может содержать секрет: перед логированием проверяем её состав, иначе пишем безопасный код или тип.
- Клиент получает понятную публичную ошибку; внутренние SQL и технические подробности ему не передаются.

## 5. Context, сеть и параллелизм

- `context.Context` — первый аргумент операции с I/O. Передаём контекст входящего запроса до БД и AI, не заменяем его `context.Background()` внутри запроса.
- Context не хранится в struct; `context.Value` не служит контейнером зависимостей или параметров. У созданного timeout/cancel есть вызов `cancel` на всех путях. Основание — [документация `context`](https://pkg.go.dev/context).
- Сетевой вызов имеет ограничение времени, связанное с общим дедлайном запроса. HTTP-клиент и transport переиспользуем; тело ответа закрываем, объём чтения ограничиваем. Основание — [документация `net/http`](https://pkg.go.dev/net/http).
- Повтор внешнего вызова ограничен числом попыток и дедлайном. Запись или платную генерацию не повторяем автоматически без идемпотентности либо доказательства, что первая попытка не выполнилась.
- Goroutine запускаем только для конкретной необходимости. У неё есть владелец, способ остановки, ограничение количества и ожидание завершения; обработчик не оставляет фоновое сохранение после ответа.
- Общие данные неизменяемы либо защищены синхронизацией. При изменении параллельного поведения проверяем его race detector в CI.
- При остановке сервиса прекращаем приём запросов, завершаем доступную работу в пределах дедлайна и закрываем пул БД.

## 6. HTTP-контракт и внешние данные

- Сначала описываем изменение ручки в `shared/api/openapi.yaml`, затем согласованно меняем DTO и реализацию. Общего Go/TypeScript-кода в `shared/` нет.
- Для запросов задаём лимит тела, строго декодируем JSON, проверяем неизвестные поля там, где контракт их запрещает, и отклоняем лишние JSON-значения после ожидаемого объекта.
- Транспорт проверяет форму, предметная модель — допустимость, сценарий — доступ и сохранение. Клиентская проверка и ответ AI не заменяют серверную.
- Пагинация, загрузка файлов, время выполнения и длина пользовательского текста имеют явные границы.
- CORS — явный список origin; он не является авторизацией. Токен черновика проверяется для каждого защищённого действия независимо от origin.
- Из AI принимаем предложение по определённой схеме, проверяем его как пользовательские данные. Лор, баланс и решение о принятии предложения остаются у утверждённых правил и игрока.
- Не возвращаем персональные и мастерские данные вместе с публичной моделью.

## 7. PostgreSQL

- SQL находится в storage; используем существующий `pgx`. Пользовательские значения передаём параметрами `$1`, `$2`, а не конкатенацией или `fmt.Sprintf`. Динамические имена столбцов выбираем только из разрешённого набора. Основание — [рекомендации Go против SQL injection](https://go.dev/doc/database/sql-injection).
- Перечисляем столбцы явно. Длинные запросы оформляем читаемым многострочным SQL.
- Операции, составляющие одно сохранение, выполняем в одной транзакции. Все запросы этой операции используют один `tx`; успешный ответ даём только после проверенного `Commit`. Основание — [руководство по транзакциям Go](https://go.dev/doc/database/execute-transactions).
- Заранее предусматриваем rollback на ошибке и освобождение соединения, включая отмену запроса. Для pgx не предполагаем автоматический rollback при отмене context; правила жизненного цикла сверяем с [контрактом `pgx.Tx`](https://pkg.go.dev/github.com/jackc/pgx/v5#Tx).
- `Rows` закрываем и проверяем `Rows.Err()`. Отсутствие строки переводим в предметный результат, не выдаём ошибку драйвера наружу.
- Конкурирующие завершения черновика решаем блокировкой/ограничением на уровне БД. Проверка «сначала прочитал — потом записал» без защиты не гарантирует целостность.
- Пул и число экземпляров учитывают лимит соединений PostgreSQL; дополнительная параллельность HTTP не означает неограниченный пул.
- Изменение схемы — новая последовательная миграция. Применённые миграции не редактируем; приложение не мигрирует БД автоматически при запуске.
- Runtime работает под ограниченным пользователем; реквизиты поступают из окружения/Lockbox, TLS проверяет сертификат и имя хоста.

## 8. Тесты и приёмка

- Тестируем наблюдаемое поведение: границы бюджета, HP/AC, невалидные данные, доступ к чужому черновику, отмену, атомарность и повтор завершения. Тест не повторяет алгоритм реализации.
- Для набора случаев используем table-driven tests и `t.Run`; проверяем конкретный результат и ошибку. Сообщение показывает вход, `got` и `want`. Тестовые помощники отмечаем `t.Helper`.
- Используем стандартный `testing`, `httptest` и небольшие подмены реальных границ. Не вводим библиотеку утверждений или генерируемые моки только ради простого теста. Эти подходы опираются на [Google Go Best Practices](https://google.github.io/styleguide/go/best-practices).
- Тест не зависит от production-БД, живого AI, времени ожидания через `sleep` и чужих данных. Интеграционные SQL-тесты запускаем на отдельной тестовой БД с известными миграциями.
- Изменение параллелизма дополнительно проверяем `go test -race ./...` в CI. Тесты доступа и атомарности обязательны для затронутых сценариев.

Чек-лист:

- [ ] У пакета и функции одна понятная ответственность; HTTP, сценарий и SQL разделены.
- [ ] Зависимости явные, интерфейсы небольшие; нет глобального изменяемого состояния.
- [ ] Контракт YAML и реализация совпадают, лимиты и публичные ошибки определены.
- [ ] Ошибки, context, закрытие ресурсов и завершение транзакции обработаны.
- [ ] Секретов и сырых пользовательских данных в коде, ответах и логах нет.
- [ ] Поведение с существенными последствиями покрыто тестами.
- [ ] Форматирование `gofmt` проверено; `go test ./...`, `go vet ./...` и сборка прошли в CI.

По текущему решению пользователя сборки и тесты выполняются в CI. Локальные сборки не возобновляем без его явного указания. Для изменения только документации сборка сервиса не требуется.

CI проверяет `gofmt` для новых Go-файлов перед тестами и деплоем. Исходная граница — [code-style-baseline.json](code-style-baseline.json), список семи существующих Go-файлов на коммите `0d27157c776a701528c7716c8293f59ed74f019f`. Эти пути исключены из новой проверки даже при изменении: текущий код не требует рефакторинга ради CI. Новые пути проверяются целиком на каждом запуске, поэтому ранее добавленный файл не выпадает из контроля на следующем коммите. Форматирование проверяется без изменения файлов; тесты проверяющего скрипта покрывают исключение старого кода и обнаружение нового неформатированного/невалидного кода.

Список исключений не пополняем при обычной разработке. Новый или переименованный Go-файл обязан пройти форматирование. Архитектура, обработка ошибок и границы пакетов проверяются при ревью. Go-тесты в проверке и деплое выполняются с race detector; HTTP/SQL-сценарии используют временную PostgreSQL внутри CI, а ответы сверяются с OpenAPI. Новые CI-проверки фронтенда отложены по решению пользователя.
