# Правила нового фронтенд-кода

Обязательные соглашения для нового и существенно изменяемого кода в `frontend/`. Общие правила проекта находятся в [AGENTS.md](../AGENTS.md).

Существующий фронтенд целиком не переписываем. Старый большой компонент не служит образцом для нового. При расширении старого экрана новую самостоятельную часть оформляем по этим правилам; необходимое изменение старого кода ограничиваем задачей.

## 1. Границы FSD

Порядок зависимостей: `app → pages → widgets → features → entities → shared`. Можно пропускать слои и импортировать более низкий напрямую. Слайсы одного слоя независимы: один feature не импортирует другой feature, одна page — другую page. Общую композицию переносим выше, общую предметную модель — ниже. Это следует [правилу изоляции слайсов FSD](https://feature-sliced.design/docs/reference/slices-segments).

| Место | Что хранит |
| --- | --- |
| `app` | Маршруты, провайдеры, инициализацию приложения |
| `pages/<slice>` | Композицию конкретной страницы |
| `widgets/<slice>` | Самостоятельные крупные блоки интерфейса |
| `features/<slice>` | Действие пользователя: сохранение черновика, выбор класса |
| `entities/<slice>` | Предметные типы, данные и отображение персонажа, расы, навыка |
| `shared` | Технические примитивы без знаний о персонажах и правилах игры |

Внутри слайса используем сегменты по ответственности:

- `ui` — компоненты и их CSS Modules;
- `model` — состояние, хуки поведения, предметные типы и вычисления;
- `api` — запросы, транспортные типы, преобразование ответов;
- `lib` — внутренние чистые вспомогательные функции;
- `config` — настройки и константы этого слайса.

Создаём только нужные сегменты. Не заводим общие папки `components`, `hooks`, `types`, `helpers` вне конкретной ответственности. `shared/lib` группируется по назначению, например `date` или `http`; формулы характеристик принадлежат предметной модели, а не `shared`.

## 2. Компонент и его публичный экспорт

Каждый новый компонент имеет собственную папку:

```text
features/save-character/ui/SaveCharacterButton/
  SaveCharacterButton.tsx
  SaveCharacterButton.module.css
  index.ts
```

В `.tsx` разрешены только импорты, тип пропсов и один именованный компонент. Хелперы, константы, другие типы, кастомные хуки и вложенные компоненты объявляются в своих файлах. `.tsx` используем для JSX; файл без JSX имеет расширение `.ts`.

```tsx
import styles from './SaveCharacterButton.module.css';

export type SaveCharacterButtonProps = {
  isPending: boolean;
  onSave: () => void;
};

export function SaveCharacterButton({
  isPending,
  onSave,
}: SaveCharacterButtonProps) {
  return (
    <button
      className={styles.button}
      type="button"
      disabled={isPending}
      onClick={onSave}
    >
      {isPending ? 'Сохраняем…' : 'Сохранить персонажа'}
    </button>
  );
}
```

В `index.ts` компонента — только явные реэкспорты:

```ts
export { SaveCharacterButton } from './SaveCharacterButton';
export type { SaveCharacterButtonProps } from './SaveCharacterButton';
```

У каждого нового слайса также есть корневой `index.ts`, который экспортирует только используемый снаружи API. Внешний потребитель импортирует из корня слайса, а не из его `ui`, `model` или `api`. В `shared/ui` и `shared/lib` каждый самостоятельный модуль имеет отдельный `index.ts`; общего экспорта всех компонентов приложения нет. Принцип основан на [публичном API FSD](https://feature-sliced.design/docs/reference/public-api).

Правила импортов:

- снаружи слайса — только его публичный API;
- внутри слайса — относительные пути; соседний компонент импортируем через его папку с `index.ts`, хук или хелпер — из конкретного файла;
- компонент не импортирует собственный `index.ts`, слайс не импортирует свой корневой `index.ts`: это создаёт циклы;
- никаких `export *`, логики, инициализации и побочных эффектов в `index.ts`;
- используем именованные экспорты и `import type` для типов;
- используем настроенные в проекте пути; псевдоним `@/` без настройки Vite и TypeScript не предполагаем.

## 3. Размер и ответственность

Для написанного вручную нового `.tsx` цель — **30–60 строк**, верхняя граница — **100 строк всего файла**, включая импорты, пропсы и пустые строки. Это проектное ограничение, которое делает компонент обозримым примерно на одном экране редактора.

- Один компонент решает одну интерфейсную задачу. Страница собирает блоки, а не содержит всю форму, запросы и правила её заполнения.
- При превышении границы выделяем осмысленную секцию интерфейса или выносим поведение в модель. Не сокращаем число строк уплотнением JSX, удалением отступов или переносом огромного компонента в один хук.
- Новый хук или хелпер тоже решает одну задачу. Файл `.ts` ориентировочно до 200 строк; более крупный модуль разделяем по ответственности. Цель функции — до 40 строк; длинная функция требует пересмотра границ.
- Условия показываем простыми ветками. Вложенные тернарные операторы и большие выражения внутри JSX запрещены.
- Не создаём универсальную абстракцию ради одного применения. Выделенный блок должен иметь понятное имя и собственную ответственность.

## 4. Логика и состояние

Компонент показывает данные и связывает события с моделью. Внутри допустимы короткие UI-обработчики, например передача `event.target.value`, и простое локальное состояние открытия панели. Сценарий сохранения, валидация, расчёт баланса, работа с хранилищем и сетью находятся вне `.tsx`.

- Предметные вычисления — чистые функции в `model`; форматирование и технические преобразования — в `lib` соответствующего модуля.
- Состояние формы и переходы шагов — в `model/use…` или reducer. Reducer и его типы лежат отдельно от компонента и хука.
- HTTP-функции — в `api`; общий HTTP-клиент — в `shared/api`. Компоненты не вызывают `fetch` и не собирают адреса ручек.
- Побочные эффекты браузера находятся в хуках: подписки, таймеры, чтение и запись сохранённого состояния. У них есть очистка и обработка ошибки.
- Состояние не мутируем, побочные эффекты во время рендера не выполняем. Основание — [правила чистоты React](https://react.dev/reference/rules/components-and-hooks-must-be-pure).
- Производные значения вычисляем из исходных данных. Не дублируем их в состоянии и не синхронизируем цепочкой `useEffect`. Эффект нужен для синхронизации с внешней системой; действие игрока обрабатывается событием. Основание — [рекомендации React об эффектах](https://react.dev/learn/you-might-not-need-an-effect).
- `useMemo`, `useCallback` и `memo` добавляем при конкретной необходимости, а не ко всем функциям и компонентам.

## 5. Типы, данные и HTTP

- TypeScript работает в `strict`. Запрещены `any`, двойные приведения `as unknown as …` и подавление ошибок вместо описания реального типа.
- На внешней границе используем `unknown`, проверяем форму данных и только затем преобразуем в предметную модель. Приведение типа не является валидацией ответа.
- Тип пропсов называется `ComponentNameProps` и находится в файле компонента. Общие предметные типы — в `model`, транспортные — в `api`.
- Состояния запроса описываем явно: загрузка, успех, ошибка. Если сочетания булевых флагов допускают невозможное состояние, используем discriminated union.
- Источник HTTP-контракта — [OpenAPI YAML](../shared/api/openapi.yaml). TypeScript-типы и клиент находятся только во `frontend/`; в корневой `shared/` исполняемый TypeScript не появляется.
- Лор и утверждённые значения читаем из `content/` или API каталога. Не копируем каталог классов, бюджет очков и формулы в компонент.
- Сервер окончательно проверяет баланс, доступ и сохранение. Клиентская проверка даёт обратную связь игроку.
- Обрабатываем HTTP-ошибки, отмену устаревшего запроса и повторное нажатие сохранения. Токен черновика не помещаем в URL, сообщения и логи.
- Пустая выдача, ошибка и загрузка имеют отдельное отображение. Для списков используем стабильный `id` как `key`.

## 6. Стили и доступность

- `Component.module.css` хранится рядом с компонентом. Стили его самостоятельного дочернего блока находятся у дочернего компонента.
- Цвета, прозрачности, градиенты и тени берём из `src/shared/styles/variables.css`. Прямые цветовые значения в CSS Modules запрещены.
- У кнопок и полей есть доступные подписи, у фокуса — `focus-visible`; действие доступно с клавиатуры. Используем нативную семантику: кнопку для действия, ссылку для перехода.
- Не добавляем UI-библиотеку, глобальные классы и inline-стили для статического оформления. Динамическая геометрия может передаваться через CSS-переменные.
- Проверяем длинные тексты и мобильную ширину. Игровые компоненты и UX-инварианты из `AGENTS.md` сохраняют обязательность.

## 7. Приёмка изменения

Перед сдачей нового кода проверить:

- [ ] FSD-слой выбран правильно; обратных зависимостей, связей между слайсами одного слоя и обходов публичного API нет.
- [ ] У компонентов и слайса есть явные экспорты через `index.ts`.
- [ ] В `.tsx` только импорты, пропсы и один компонент; файл укладывается в 100 строк.
- [ ] Поведение, запросы, типы и вспомогательные функции лежат по ответственности; нет безымянного набора `utils`.
- [ ] Контракт, каталог и серверные правила не продублированы в UI.
- [ ] Есть загрузка, пустое состояние, ошибки и защита от повторного сохранения.
- [ ] Значимые новые вычисления и переходы состояния проверены тестами поведения; простую разметку не покрываем тестами, повторяющими её реализацию.
- [ ] Обязательные `typecheck`, `build`, `build:pages` прошли в CI; затронутый UI проверен встроенным браузером по `AGENTS.md`.

По текущему решению пользователя сборки и тесты выполняются в CI. Локальные сборки не возобновляем без его явного указания. Для изменения только документации сборка приложения не требуется.

Эти соглашения обязательны при ревью. Сейчас CI не проверяет автоматически размер компонентов, FSD-границы и состав `.tsx`; включение соответствующих проверок — отдельная задача.
